# Maintaining the Codex compatibility fork

The `codex-compat` branch in [lovinrain/copilot-api](https://github.com/lovinrain/copilot-api/tree/codex-compat) carries the Copilot Responses compatibility patch independently of upstream. Upstream [PR #430](https://github.com/caozhiyuan/copilot-api/pull/430) was closed without merging.

## Branches and source revisions

| Branch | Purpose |
| --- | --- |
| `codex-compat` | Maintained branch for this patch, starting from upstream v2.7.11 (`ce13231`) plus compatibility commit `b2dd4af`. CI runs on every push. |
| `fix/codex-collaboration-compat` | Original upstream submission, retained at `b2dd4af5984b995c9d17abb4deee9628cf165476`. |
| `fix/codex-collaboration-compat-v2.6.20` | Source of the deployed `2.6.20-codex-compat.1` backport, retained at `ec5a62356b74d260a4897313f56fcb2045316132`. |

The fork's existing `dev` branch has a separate startup fix and is not the maintenance branch for this feature. Updating `codex-compat` does not deploy a new server version. The v2.6.20 branch records the deployed source; use a new branch for subsequent backports so this revision remains easy to recover.

This branch intentionally starts from the already validated v2.7.11 baseline. New upstream commits are incorporated through the update procedure below after validation.

## Run the patched gateway

Use this fork's source. The upstream npm package and upstream prebuilt images do not include this downstream patch.

```sh
git clone --branch codex-compat --single-branch https://github.com/lovinrain/copilot-api.git copilot-api-codex-compat
cd copilot-api-codex-compat
bun install --frozen-lockfile
bun run start start
```

Bun 1.4.3 is the CI baseline. The second `start` is the gateway CLI subcommand. Reuse your existing gateway configuration and credentials; see [installation and startup](docs/guides/en/getting-started.md) for first-time setup.

To build a local container from this checkout:

```sh
docker build -t copilot-api:codex-compat .
```

Use that image with your existing deployment configuration and persistent data mount. Pin the chosen source commit or image digest for deployment. The inherited release workflows are not a configured publication channel for this fork's patch; maintaining this branch does not publish an npm package or an automatic release.

## Enable only the affected models

Add exact resolved Copilot model IDs to the gateway configuration:

```json
{
  "copilotResponsesCompatibilityModels": ["gpt-6-astra"]
}
```

Restart the gateway after editing its configuration. Enable compatibility for every model that produces or consumes the affected delegation messages. The allowlist is checked after model mapping. A separately mapped approval-review model may also need inclusion if it replays those messages; that workflow has not been validated by the recorded live tests.

The mode is backward compatible by default: the list defaults to `[]`, and existing workflows outside the opt-in native Copilot Responses path retain their behavior. No known regressions were found in the tests and live checks described below.

When enabled, the patch:

1. Aliases the reserved collaboration tools so Copilot produces plaintext delegation messages, then restores Codex's original tool names.
2. Persists hashes of those new messages before returning completed calls. It uses the hashes to correct Codex's later `encrypted_content` label to `input_text`, preserving the exact message.
3. Returns qualifying early invalid-request errors as HTTP 400 before committing streaming headers, preserving the useful diagnostic through a relay.

See the [compatibility guide](docs/guides/en/copilot-collaboration-compatibility.md) for protocol behavior and stream limits.

## Data and recovery constraints

Preserve the gateway's SQLite database across restarts and migrations. The new `copilot_plaintext_collaboration_messages` table stores hashes, not message bodies, in `COPILOT_API_SQLITE_DB_PATH` or the default `copilot-api.sqlite` data file. Resumed requests need an instance containing their hashes. This fork does not provide a distributed metadata service.

Delegation messages generated by this mode are plaintext in the client history. Existing unknown ciphertext is not decrypted or discarded. The patch does not make encrypted reasoning interchangeable across accounts or providers.

Removing a model from the allowlist restores the original handling for that model, but it does not migrate compatibility-generated history back to native ciphertext. Keep the mode and its metadata available for sessions that depend on them. A rollback must account for those sessions as well as the server image.

## Incorporate upstream changes

Use a clone where `origin` is this fork and `upstream` is `caozhiyuan/copilot-api`. Add the upstream remote once if it is missing:

```sh
git remote add upstream https://github.com/caozhiyuan/copilot-api.git
```

Create a review branch from the current maintained branch:

```sh
git fetch origin codex-compat
git fetch upstream dev
git switch codex-compat
git pull --ff-only origin codex-compat
git switch -c sync/codex-compat-YYYYMMDD
git merge --no-ff --no-commit upstream/dev
```

Replace `YYYYMMDD` with the update date. Resolve conflicts using the incoming upstream behavior and the compatibility requirements below. Record the new upstream base in this document, then commit the merge, push the review branch, and open a PR **in this fork** targeting `codex-compat`. Merge after review and green CI.

Preserve the maintained branch's history. Replacing it wholesale with upstream would remove the downstream patch. Check these areas on every update:

- Collaboration definitions in top-level tools, additional/discovered tools, history, and tool choices still receive consistent namespace translation.
- Completed message hashes are persisted before Codex can start a child; only recognized `agent_message` content is relabeled.
- Streaming and nonstreaming results preserve argument strings, call IDs, ordinary tools, and unknown encrypted content.
- Early error inspection still preserves ordering, pending reads, cancellation, usage, and its time/buffer limits.
- Default configuration and other models/providers/protocols bypass compatibility, and this fork's CI trigger remains enabled.

## Validation

The branch CI uses Node.js 22.18.0 and Bun 1.4.3 and checks gateway/desktop lint, gateway/desktop types, the full test suite, and the package build. The workflow can also be dispatched manually on this branch.

For local validation after merging upstream:

```sh
bun install --frozen-lockfile
bun install --cwd desktop --frozen-lockfile
bun run lint:all
bun run typecheck:all
bun test --coverage tests/collaboration-compat.test.ts tests/collaboration-message-store.test.ts tests/copilot-compat-config.test.ts tests/early-response-error.test.ts tests/responses-handler.test.ts > /tmp/copilot-compat-targeted.log 2>&1
bun test tests desktop/tests > /tmp/copilot-compat-suite.log 2>&1
bun run build
bun run build:desktop
```

Inspect test summaries and any failures in the captured logs. Meet the changed-code coverage requirement in [AGENTS.md](AGENTS.md). Before changing a deployed version, also validate a disposable parent/child lifecycle through the complete relay route: spawn, follow-up, queued message, client resume, and child resume after a gateway restart. Preserve the database during that restart.

Recorded validation for the starting revisions:

| Revision | Evidence |
| --- | --- |
| v2.7.11 compatibility patch `b2dd4af` | [Upstream PR CI](https://github.com/caozhiyuan/copilot-api/actions/runs/38096363720): 1,984 tests passed, 0 failed, on Bun 1.4.3. The five focused files passed 109 tests locally; changed executable-line coverage was 644/647 (99.54%). |
| Deployed v2.6.20 backport `ec5a623` | 1,103 tests passed before deployment. Live checks covered parent/child messaging, resume across client and gateway restart, ordinary tools, images, and a roughly 164k-token history. |

The v2.7.11 source and the deployed v2.6.20 backport are separate builds. The local Bun 1.4.2 full-suite run had the same ten existing configuration-test failures on both upstream and the patch; it was not a fully green run. Automatic approval review and arbitrary account/provider migration were not covered by the recorded live checks.

## Retire the patch only after validating a replacement

If upstream adds equivalent support, test it against the existing regression cases and actual saved compatibility sessions before removing the adapter. Native support for new encrypted messages alone does not migrate the plaintext messages already present in client histories. Retain recognition metadata and the necessary replay handling until those sessions have been migrated or retired.
